# Тестовое задание: ручной табель сотрудников

**Ожидаемое время:** 3–5 часов.

Это стартовое решение содержит минимальный WPF-клиент и каркас ASP.NET Core API. В стартовом коде намеренно присутствует некорректное прикладное поведение. Ваша задача — воспроизвести его как пользователь, диагностировать, исправить и защитить исправления автоматическими тестами.

## Запуск и порядок работы

Для запуска требуются .NET SDK, targeting pack для `net6.0` / `net6.0-windows` и доступ к NuGet.

1. Откройте `TimesheetCandidateTask.sln` в Visual Studio и назначьте `TimesheetCandidateTask.Wpf` запускаемым проектом. Для воспроизведения исходного WPF-сценария запустите именно этот проект: отдельный процесс API на этом этапе не требуется.
2. Нажмите «Загрузить» на экране «Табель выхода сотрудников» и воспроизведите сценарии из следующего раздела.
3. Исследуйте WPF-клиент, доменную модель и прикладную логику, исправьте поведение и добавьте тесты.
4. После исправления локальной логики выполните следующий обязательный этап: подключите WPF-клиент к `TimesheetCandidateTask.Api` и вынесите в API операции получения, сохранения, добавления строки и изменения комментария; добавьте API-тесты.

Команды из корня решения:

```text
dotnet build TimesheetCandidateTask.sln
dotnet test TimesheetCandidateTask.sln
dotnet run --project src/TimesheetCandidateTask.Wpf
```

Для отдельной проверки API запустите его в другом окне терминала:

```text
dotnet run --project src/TimesheetCandidateTask.Api --launch-profile TimesheetCandidateTask.Api
```

Профиль `TimesheetCandidateTask.Api` из `src/TimesheetCandidateTask.Api/Properties/launchSettings.json` запускает API по адресам `https://localhost:52136` и `http://localhost:52137`. Swagger доступен по адресу `https://localhost:52136/swagger` или `http://localhost:52137/swagger`.

## Экран табеля

Клиент показывает табель торговой точки за январь 2026 года: сотрудника, часы и комментарии за 01.01 и 02.01, итоги по строке и по табелю. Доступны статус «Черновик» / «Утверждён», а также кнопки «Загрузить», «Добавить сотрудника», «Сохранить» и «Утвердить».

Клиент использует общую доменную модель и расчёт итогов API-проекта. Локальное демонстрационное хранилище оставлено компактным, чтобы WPF-сценарий запускался без отдельного процесса API.

## Наблюдаемые пользовательские сценарии

В исходном состоянии убедитесь в следующем:

1. Нажмите «Добавить сотрудника» дважды. В таблице появляются повторяющиеся строки одного сотрудника, а итог по табелю меняется.
2. После «Загрузить» обратите внимание на строку с часами за 01.01 и 02.01. Общий итог выглядит больше фактически указанных часов.
3. Измените комментарий за 01.01 и нажмите «Сохранить». Введённый текст отображается у 02.01. Затем измените комментарий за 02.01 и сохраните: интерфейс сообщает, что обновить комментарий не удалось.

Не ограничивайтесь изменением интерфейса: поведение должно быть исправлено в соответствующей прикладной логике и согласовано с API.

## Обязательная API-часть

Проект `src/TimesheetCandidateTask.Api` — контроллерный каркас ASP.NET Core 6 с SQLite и Swagger. Доведите контракт и реализацию до состояния, в котором доступны и проверены:

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/api/timesheets?retailId={guid}&periodStart={date}` | Получить табель за точку и месяц. |
| `PUT` | `/api/timesheets` | Создать или сохранить табель. |
| `POST` | `/api/timesheets/{retailId}/{periodStart}/lines` | Добавить строку сотрудника. |
| `PUT` | `/api/timesheets/{retailId}/{periodStart}/lines/{lineId}/comment` | Изменить комментарий конкретного дня строки. |

Контракты запросов и ответов доступны в Swagger. Период передаётся первым днём месяца. Табель в статусе `Approved` нельзя изменять ни сохранением, ни добавлением строки, ни обновлением комментария: API должен вернуть понятный конфликт.

Демонстрационные параметры API:

```text
retailId: c4335485-a459-424f-90fc-8e8e4445f121
periodStart: 2026-01-01
```

SQLite-файл создаётся рядом с API-проектом при первом запуске. Для возврата к начальному API-состоянию удалите `src/TimesheetCandidateTask.Api/timesheet-task.db` и повторно запустите API.

## Границы задания

Не требуются:

- авторизация и роли;
- реальная БД для развёртывания, миграции или внешние интеграции;
- печать, Excel и другие выгрузки;
- полный календарь месяца: в WPF достаточно двух отображаемых дней;
- переработка legacy-кода или смена целевых платформ `net6.0` и `net6.0-windows`.

## Допустимые предположения

- Одна строка сотрудника в пределах табеля определяется `EmployeeId`; повторная строка для того же сотрудника не нужна.
- Дневные данные относятся к месяцу табеля; это правило можно валидировать на сервере.
- `HolidayHours` — отдельный показатель часов в праздничные дни, а `TotalHours` — общий объём фактически отработанных часов.
- При конкурентных запросах сервис не должен создавать логически повторяющиеся данные.

## Критерии сдачи

- WPF-сценарий понятен, запускается и после исправления отражает корректные данные.
- Устранены причины всех наблюдаемых сценариев, а не только их отображение в UI.
- API содержит согласованный контракт операций GET, PUT, создания строки и изменения комментария; для недопустимых изменений `Approved` возвращаются подходящие ошибки.
- Добавлены читаемые автоматические тесты на пользовательские сценарии и исправленное поведение, включая API-тесты.
- Сохранены `net6.0`, `net6.0-windows`, SQLite и контроллерный API; зависимости и объём решения не разрослись без необходимости.
- В решении кратко описаны принятые предположения и выполненные проверки.
